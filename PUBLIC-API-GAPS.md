# Public API Gaps

1. **Counselor capabilities by session mode** — `GET /booking/counselors/{counselor}/services` returns counselor-specific services and prices but no supported session modes. The reservation endpoint accepts `mode` and `session_mode`, but there is no public capability contract for each counselor/service pair. Current UI must offer the backend's accepted modes without claiming counselor-specific support.
2. **Payment method availability for clients** — gateway status is exposed through the admin-only `/admin/booking/gateways`; there is no public endpoint listing enabled client payment methods. The frontend therefore follows the single checkout URL returned by the payment initiation endpoint and does not render a provider selector.
3. **Specialty detail resource** — only `GET /specialties` is registered publicly. Specialty detail is derived from the published specialty collection; no dedicated slug lookup, descriptive copy, SEO fields, or pagination contract is exposed.
4. **Client payment lookup by payment ID** — payment history is scoped to a booking (`GET /booking/my-reservations/{booking}/payments`). The Fake Bank return includes `payment_id` but no booking ID, so the frontend must enumerate the client's own paginated reservations and payment lists to find that attempt. A client-owned payment lookup endpoint would avoid N+1 API calls.
5. **Public center profile/settings** — center address, contact information, cancellation policy and connection-release configuration are currently admin-only settings or CMS-managed. Public UI can only show content explicitly published through CMS or returned on the authorized appointment.
6. **Attendee intake during booking** — `POST /booking/reservations` accepts counselor, service, slot, mode, payment option and promo code. It does not accept attendee detail/intake answers. The client account is the attendee identity; intake forms are separate and require a form identifier.
7. **Notification preference scope** — the client endpoint currently exposes only `sms_enabled`; email/push choices and actual reminder delivery receipts are not part of this public contract.
8. **Pagination contract shape** — several endpoints return Laravel paginator shapes while others wrap lists under `data`; frontend wrappers normalize known shapes but this remains an endpoint-specific contract.
9. **Variable duration and atomic multi-booking** — public availability and `POST /booking/reservations` accept one `service_id` and one `starts_at`; duration and price come from that service. There is no request field for a variable duration or a batch of start times. The frontend can reserve multiple selected times only as separate, sequential booking requests, with separate payment pages. If a later request fails, earlier reservations remain active and the UI reports them explicitly; a backend batch endpoint with all-or-nothing reservation would avoid partial multi-bookings.

No backend files were modified. Zarinpal and SnappPay are deliberately fail-closed in the backend and require provider contracts/credentials before activation.
